## 一、3 个问题与根因

### 债 1（P2）：`score_threshold` 硬编码 8.0，daily_digest 无法配置

- **位置**：`agents/workflow/loop_node.py:19,45`；`agents/pipelines/daily_digest.py:271-280`
- **现状**：`LoopSpec.score_threshold = 8.0`（line 19 dataclass 默认）；`_coerce_loop_spec` 从 `step.config["loop"]["score_threshold"]` 读取，但 `build_daily_digest_workflow` 构造的 curate step 永远不传 `config`
- **后果**：daily_digest 只能接受默认 8.0 的阈值，operator 调不到更严/更松的标准

### 债 2（P2）：`publish_history` 无 `(publisher_id, digest_date)` 唯一约束

- **位置**：`core/publish_history.py:21-26`；`infra/db.py:378-394`
- **现状**：表只有 `id` PK 和 2 个非唯一索引；每次 `add()` 生成新 uuid4（line 87），导致重跑会重复记录同一发布
- **后果**：调度重跑/手动回放/定时失败重试 → publish_history 表累积重复行，无法做幂等去重

### 债 3（P2）：Reflection 输出固定 512 token 截断，不可配

- **位置**：`agents/executor.py:529`
- **现状**：`min(512, output_reserve, ...)` 硬编码 512
- **后果**：长反思被截断，影响质量评估精度

## 七、风险与取舍

1. **publish_history 加列迁移**：既有 SQLite 表可能已有数据，`ALTER TABLE ADD COLUMN` 幂等处理用 try/except；唯一索引用 `CREATE UNIQUE INDEX IF NOT EXISTS`。
2. **UNIQUE 与现有重跑兼容**：现有发布未带 digest_date 时，迁移后该列是 NULL，NULL 不参与 UNIQUE 约束（SQLite/Postgres 都如此），所以现有数据不会触发冲突。
3. **Reflection 上限默认值**：保持 512 不变；用户可调高但默认是安全值。
4. **P31 原 4 个 P0 问题（dedup_key / 全失败保护 / 空候选拦截 / LLM 契约校验）** 不在本包，留待独立排期。
